# 架构骨架质量评测

## 结论

当前骨架按“后端领域骨架”标准可以进入开发阶段，但不按“完整产品架构”评为满分。

综合评分：`92 / 100`

开工结论：可以开工，但第一批开发必须优先补齐数据库、租户隔离、权限边界、输入校验和业务服务层，不能直接进入小程序前台。

## 评分明细

| 维度 | 分数 | 说明 |
| --- | ---: | --- |
| 领域建模 | 18 / 20 | 已覆盖俱乐部、人员、球队、活动、训练、比赛、指标、评测和派生数据。 |
| 多俱乐部解耦 | 18 / 20 | 已有 `clubId`、`CatalogScope`、功能开关、策略、自定义字段，但还没有数据库级隔离和权限执行。 |
| 扩展性 | 18 / 20 | 运营、AI、媒体、支付、场地都能通过事件和外键扩展，不侵入训练核心。 |
| 技术可演进性 | 16 / 20 | monorepo、领域包、API 壳和测试已建立，但缺少持久化、OpenAPI/Schema、服务层约束。 |
| 测试与验证 | 12 / 15 | 有类型检查、领域单测、API 单测和运行时验证；需要补集成测试和数据隔离测试。 |
| 开发连续性 | 10 / 15 | 文档清楚，但开发窗口需要统一任务边界，避免并行改同一批文件。 |

## 通过项

- `pnpm check` 通过。
- `pnpm build` 通过。
- 统一活动日历模型成立。
- 学员多球队、训练、比赛、其他活动可以共享参与模型。
- 球员指标数据已经原子化，派生指标保留血缘。
- 多俱乐部边界已经前置。
- API 已经改成俱乐部作用域路径。

## 主要风险

### 1. 没有持久化层

当前 API 使用内存种子数据。下一步必须建立数据库 schema、迁移、仓储接口和测试数据，否则业务 API 很快会被临时实现污染。

> 时效说明（2026-07 交接时补充）：该风险已解决。`apps/api` 现已具备 SQLite 持久化、6 个版本化迁移（`src/migrate.ts`）和仓储层（`src/persistence/`）。本节其余内容为评测时点（骨架阶段）的历史结论。

### 2. 没有权限执行

已经有 `ClubUserMembership`，但还没有真正的认证、授权和资源访问判断。多俱乐部项目里这是第一优先级风险。

### 3. 没有输入契约

当前 API 没有请求/响应 schema。后续小程序、管理后台、AI 模块都会依赖 API 契约，应尽早加入 schema 校验和 OpenAPI 输出。

### 4. 业务服务层不足

当前领域模型主要是类型和少量函数，尚未形成应用服务，例如创建活动、记录比赛事件、录入评测、计算派生指标。下一步开发应该把这些操作沉淀为服务层。

### 5. 目录覆盖规则还没有实现

`CatalogScope` 已有类型，但还没有完整的目录解析规则，例如俱乐部覆盖系统默认项、停用某个系统项、优先选择俱乐部版本。

## 评测结论

这不是“产品级满分”，但已经满足“骨架质量通过，可以进入后端 MVP 开发”的门槛。

后续不应先做微信小程序。第一阶段应先做后端基础能力、管理 API 和核心业务服务，确保前端进场时 API 和数据边界稳定。
