# 服务器当前发布代码与最新版产品设计：遗漏评估

日期：2026-09-19。按用户纠正，直接检查服务器代码，不以微信操作、旧 Figma 或本机未部署代码代替线上基线。本轮只评估，不改业务源码、Figma、服务配置或生产数据。

## 结论

**有需要补齐的地方。最大的风险是旧页面被映射到一个新页面后，原来承载的能力被当作已经覆盖。** 服务器代码验证了上一轮的队伍能力、连续录入、比赛详情等问题，也发现私教供给信息、保险提醒、异常恢复和历史课堂评分承接等更具体的遗漏。

这里的“遗漏”分三类：

- **新版未明确承接：** 现有能力有代码，新需求没有明确取消，但最新版页面/说明没有完整去向。
- **需求已有、页面未落实：** 不是需求漏写，应补页面入口、交互或状态。
- **主动简化后的历史承接：** 不恢复旧强制流程，保留历史事实并明确去向。

## 三、不应作为遗漏恢复的内容

1. **逐堂点名、点名扣课、请假审批。** 新需求已主动转为日期过后生成记录、双方直接修正；旧入口职责需要退出，历史记录仍保留。
2. **每课或每个训练项目必须评价。** 已明确简化为按需维护当前评价。S7 讨论旧数据承接，不要求恢复工作负担。
3. **把标准分当原始成绩，或周期到期后锁死录入。** 现有部分测评实现有这类限制，新需求已经要求改进，不应因其在线存在而继承。
4. **课包余额与自动训练课次混算。** 旧余额/提醒有价值，但展示依 O-03，不能把自动计次解释为财务扣款。
5. **固定六维、学员排名或队均值作为培养标准。** 新版按模型维度和个人历史/培养标准解释，保留这一改进。

## 四、建议逐页评审顺序

先审 **C10/C11/C16（能力查看与任务执行分开）→ C18/C20（连续输入和部分失败）→ C29/C28（接单偏好与身份入口）→ P12/P21/P24（保险与提醒去向）→ P25（到场导航）→ P03/P13（活动详情）**。旧课堂评分历史与战术板范围另做明确的保留/退出决定。

可直接加入页面评审的场景：

- 同一教练兼任家长，完成工作后能切换到自家孩子，不重新绑定账号。
- 私教意向已分派，但教练关闭接单或该时段不可用，页面能看到事实，分派不等于承接。
- 保险将到期，家长能在获准范围内查到期限与消息；不从训练次数推算保险或余额。
- 录入 5 人，2 人保存失败：已成功的 3 人保持成功，2 人草稿保留并可单独重试，然后进入下一项目。
- 名单成功、能力汇总失败：仍可进入学员，不能让整队页面不可用。
- 查看旧课堂评分：保留原课程和记录时间，不伪装成新评价或新测评。

这些是评审建议，不表示本轮已改变需求 C/P/O 状态，或开始解决开发链路。
