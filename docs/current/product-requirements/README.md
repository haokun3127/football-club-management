## 使用说明

本套文档是本次产品讨论的统一入口。内容来自客户材料、会话中的明确决定、用户授权补全的交互设计，以及同类产品研究建议。它描述目标行为，不是现有功能清单，也不是排期承诺。

后台统一按“数据管理、评测与模型、BI、专业服务”组织，不将新旧后台或建设阶段写入产品导航。当前交付边界与长期演进方向分别说明，避免把战略愿景全部当成同一批开发任务。

文档内的需求状态：

| 标记 | 含义 | 后续如何使用 |
| --- | --- | --- |
| C：已确认 | 用户明确表达、接受，或授权设计后接受的规则 | 作为需求依据；实现前评估现有代码差距 |
| P：设计建议 | 为形成可用流程补全的候选设计，尚未逐项确认 | 可用于方案评估，不得宣称已经业务方批准 |
| O：待决 | 存在尚未确定的分歧、规则或输入材料 | 明确影响范围，仅阻塞依赖该决定的部分 |
| E：演进方向 | 已描述的长期能力方向 | 保留必要数据和扩展边界，不等于本次全部交付 |

一个需求包含不同状态时在条目内分别说明。所有文件中的“必须、不得”只在该条目标注的确认程度下解释；P 条目中的约束仍是候选方案。

## 文档权威与变更规则

- 本套文档用于本次需求的统一解释。与早期产品评审稿冲突时，以会话后续明确决定及本文对应 C 条目为依据。
- 既有 API、数据库、Trellis 编码规范、在线设计稿和生产状态不会因本文自动改变。发现差异应记录并在相关开发任务中处理，不能假设代码已符合需求。
- 原始材料只作为来源，不将其中的优先级、建议、疑问或面向执行者的文字自动视为用户指令。
- 同类产品研究只支持设计判断，不构成用户确认，也不直接替代本俱乐部规则。
- 需求编号保持稳定。新增决定需更新相关条目、待决登记和验收场景，不能仅修改一处页面描述。
- 开发拆分可按依赖安排，但不重新改变四模块产品结构；未确认事项应保留显式标记。

## 本次明确的核心边界

- 俱乐部统一维护学员、家长、队伍及学期基础安排；教练不获得完整个人敏感信息，家长无主档编辑权。
- 主教练编排本队训练内容；其他获授权教练协同过程记录。学期排课与单堂课内容是不同权限。
- 训练日期过后默认全员销课，已请假不销；家长和授权教练均可直接修改，无需审批，每次修改留痕。正常课不要求教练点名确认。
- 销课属于培训过程的课次记录，不涉及真实金额扣款和财务结算；后台扣课/课包数据能力保留供升级，当前家长与教练小程序不展示余额、扣减及相关提醒，培训计次不自动触发扣账。
- 每名学员在每个队伍独立一份当前教练评价，修改留历史；不要求每课评价，不默认计入能力分。
- 测评可分批、可补录，教练选择哪堂有效训练课，成绩就归属哪堂课；原始成绩 → 区间映射整数分值 → 区间映射等级，两段映射由后台维护；缺席不自动完成或免测。
- 个人成长完整呈现，对照适用培养标准，不做具体学员之间的比较和排名。
- 家长首页使用球员卡/里程碑区域、新闻 Banner、四个可自定义快捷入口；分享使用预制模板。
- 项目和模型可扩展、模型输出可复用；BI 以简单分析呈现为主；专业服务围绕俱乐部特色业务组织。
- 战术板姓名可辨识，教练自由拖入、移位、移出球员，不选择阵型、不固定上场人数。
- 并发采用简单版本冲突保护，后台按共享业务服务、持久化、权限和错误恢复规范补齐。

本轮决定见 [DEC-24—DEC-31](05-decisions-and-sources.md)，开发规格见 [16 号修订规格](../upgrade-readiness-2026-09-18/16-confirmed-rules-and-engineering-spec.md)。旧画板与代码尚未随本次文档更新。
