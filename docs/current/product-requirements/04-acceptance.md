# 04 产品验收场景与覆盖

本文将需求转成可验证的业务结果，不是已执行测试报告。全部场景当前状态均为“待执行”。需求编号对应 [01](01-product-and-miniprogram.md) 与 [02](02-backoffice.md)，数据口径见 [03](03-data-and-permissions.md)。

## 1. 验收方式与适用边界

- C 条目的已确认行为可直接作为验收依据；包含 P 的具体交互或公式先评审，再固化预期。
- 依赖 O 的场景明确标记，不用开发者自行猜测规则补齐测试。
- E 方向只验证已纳入具体交付的能力，不将设备或 AI 愿景自动加入本次软件验收。
- 每次执行记录版本、环境、角色、测试对象、步骤、实际结果和截图/日志。异常需可复现，权限验证包含接口和导出，不能只看页面。
- 以下用例可拆分为自动测试及人工验收。是否自动化由实际改动决定，不要求为所有纯展示条目重复编写低价值测试。

## 2. 建议测试数据

采用虚构资料，准备两个俱乐部、每个俱乐部至少一支队；俱乐部 A 有队伍 A1/A2、主教练 H1、同队教练 C1、无关队教练 C2，以及不同权限管理员。家长 P1 绑定两个孩子，P2 绑定另一个孩子；另设两个同名但不同身份的人员。

准备正式学员 S1/S2/S3、球探人员 Q1；Q1 可临时参训但无正式队伍成员关系。学期内有正常训练 T1/T2、取消训练 T0、独立比赛 M1、其他活动 E1和跨测评周期的训练 T3。

课程内容示例：X 时长 10 分钟、Y 时长 20 分钟；T1 包含 X/Y，T2 包含 X，T0 内容任意但已取消。训练日期过后，S1 在 T1/T2 自动销课，S2 在 T1 已请假不销、T2 自动销课，教练无需点名。此例用于已确定的去重与来源检查，不预定请假是否进入参与率分母。

测评任务覆盖 S1/S2/S3、两个项目 J1/J2，周期包含 T1/T2、不包含 T3。设置某人分两堂课完成、某人不测评、周期后补录及一个修订草稿。模型和目标采用明确标为测试用途的假设规则，不把测试规则当成俱乐部正式评分标准。

## 10. 验收完成条件

建议按具体交付范围选取以上场景。涉及的 C 行为应通过；P 行为在评审确定后加入；未解决 O 导致的缺口应明确列出，不能标成全部通过。

验证至少涵盖管理员、主教练、同队教练、无关教练和家长角色；涉及数据修改时核对相关端及导出。UI 变更需检查真实渲染、交互、加载/错误/空态，不能仅凭代码通过认定可用。

验收结果记录应区分：通过、失败、未执行、因待决项阻塞、不适用，并附版本和证据。本次文档整理没有执行以上软件验收。
