# 数据能力与字段扩展规划

## 重新判断

客户发来的 WPS 表格不能只当成“外部导入格式”。这些字段代表一个青训俱乐部已经跑通的运营事实：谁是学员、从哪里来、在哪个区域和学校、跟哪个队训练、谁负责沟通、交了多少钱、剩多少课时、是否到课、保险是否有效、最近一次运营状态是什么。

因此平台的数据能力必须做到两件事：

1. 标准字段要覆盖主流青训俱乐部的基础运营需要，并且比客户当前表格更完整。
2. 新字段要能低成本增量添加，不能每个俱乐部一个字段就改一次核心表和前端逻辑。

这不等于 MVP 要做完整收费、保险或财务系统。MVP 的业务范围仍从训练、比赛、日程、评测开始；保险、收费和课时在 MVP 中只作为线下确认后的同步状态和运营事实承接。

## 字段分层原则

字段不按“当前客户有没有”决定是否进入核心，而按业务稳定性、查询频率和跨俱乐部复用度分层。

| 层级 | 放什么 | 存储方式 | 示例 |
| --- | --- | --- | --- |
| 核心身份字段 | 跨俱乐部稳定、权限和关联依赖 | 标准表字段 | 姓名、出生日期、性别、手机号、家长关系 |
| 青训运营字段 | 多数俱乐部都会用，影响管理视图和统计 | 标准运营扩展表 | 渠道、区域、学校、学员状态、负责教练、保险状态、课时余额 |
| 业务事实字段 | 需要审计、对账、可追溯 | 独立事实表 | 收费事件、保险购买事件、到课记录、课时流水 |
| 指标与评测字段 | 球员能力数据资产 | 指标目录 + 指标记录 | 速度、耐力、控球、传球、比赛贡献、训练态度 |
| 俱乐部个性字段 | 某个俱乐部特有或低频变化 | 类型化自定义字段 | 校区内部编号、合作学校标签、特殊备注 |
| 外部同步字段 | 对接 WPS/飞书/Excel 的来源信息 | integration/staging 表 | 外部行 ID、来源文档、字段映射版本、同步 hash |

## 从 WPS 字段吸收出来的产品能力

### 1. 学员主档

当前 `StudentProfile` 只有姓名、出生日期、性别、惯用脚、水平和备注，不够承接真实运营。

应补齐为：

- 基础身份：姓名、出生日期、性别、证件类型、证件号加密值、证件号 hash。
- 足球档案：惯用脚、当前水平、主位置、候选位置、身高、体重、入训日期。
- 运营归属：区域、学校、渠道、学员状态、默认负责教练、默认球队。
- 联系信息：主联系人、备用联系人、手机号、微信号。
- 风险与保障：保险状态、保险到期日、健康备注、紧急联系人。
- 汇总快照：累计签到、最近签到、累计充值、剩余课时、最近沟通时间。

其中证件号、手机号、微信号属于敏感信息，数据库层需要区分明文加密存储和 hash 匹配字段。

### 2. 家长与联系人

客户表里手机号和微信混在学员表中，说明他们实际需要“能联系到人”，而不是只需要家长账号。

应增加联系人模型：

- 一个学员可以有多个联系人。
- 联系人可以是父亲、母亲、监护人、本人、其他。
- 每个联系人有电话、微信、是否主联系人、是否接收通知。
- 登录账号 `UserAccount` 与联系人资料分离，避免“没有登录账号就不能维护联系人”。

### 3. 区域、学校、渠道

区域、学校、渠道不是备注字段，它们影响招生复盘、排课、球队组织和校区运营。

应作为可配置目录：

- `Region`
- `School`
- `AcquisitionChannel`

这些目录带 `clubId`，但可以预留系统级默认项。学员主档引用目录 ID，显示时保留名称快照，避免目录改名影响历史记录理解。

### 4. 学员状态与沟通反馈

“学员状态”和“沟通反馈”说明俱乐部在做轻 CRM。

标准模型应支持：

- 学员状态：潜在、试听、在训、暂停、流失、毕业、黑名单等，由俱乐部策略配置。
- 沟通记录：时间、对象、方式、内容摘要、跟进人、下次跟进时间。
- 当前沟通阶段：作为学员运营状态快照，便于列表筛选。

CRM 功能流程可以后置，但字段和数据容器要前置，否则后续导入会丢失上下文。

### 5. 收费、课时与审核

充值表反映的不是单个“支付字段”，而是三个业务事实：

- 收费事件：金额、日期、类型、缴费证明、填写人、核对人、审核状态。
- 课时入账：买了多少课时、属于哪个阶段或队伍、是否可跨队使用。
- 财务对账：公司实收、实收审核人、最终审核人、审核通过时间。

因此应拆成：

- `PaymentEvent`
- `LessonCreditLedger`
- `PaymentReview`
- `Attachment`

课时余额不要只存一个字段，应由课时入账和消课流水计算，并保留快照用于列表性能。

MVP 不发起线上收款，也不承担退款、发票或财务结算。`PaymentEvent` 和 `LessonCreditLedger` 在 MVP 中主要来自 WPS/Excel 同步或人工核对后的线下确认结果，但课时余额、入账、消课和调整必须在系统里形成可追溯状态流转，不能只做静态展示。

### 6. 出勤与消课

到课表用“第 1-27 周”宽表，是人工表格为了方便查看。但平台应存规范事实：

- 一次训练或活动是 `CalendarEvent`。
- 学员是否参加是 `EventParticipant` 或 `AttendanceRecord`。
- 是否扣课时写入 `LessonCreditLedger`。
- 周次、阶段、队伍、教练是查询维度，不应该成为固定列。

表格里的本学期签到、剩余课时可以作为快照，但权威来源应是事实流水。

### 7. 保险

保险字段是青训场景的重要运营安全能力，不应该只放自定义字段。

应支持：

- `InsurancePolicy`
- 投保日期、到期日期、保单号、保险公司、运动项目、审核状态。
- 到期提醒。
- 与学员、俱乐部、购买事件关联。

学员主档中的保险到期日是保险记录的汇总快照。

MVP 不做在线投保和理赔流程，只同步保单号、保险公司、到期日、审核状态等运营状态，用于教练和运营识别风险。

## 球员能力评估的数据能力

球员能力评估必须比普通字段扩展更严格，因为这是平台长期价值资产。

第一个俱乐部的评分表已经体现出指标图谱、测试项目、原始测试值、标准化得分、任意指标加权公式和训练建议映射。表格里的三层结构只是展示视图；底层应允许一个指标被多个体系引用，计算结果继续作为其他公式输入。详细分析见 [学员能力评估体系分析](../archive/2026-06-discovery/assessment-system-analysis.md)。

### 标准能力指标目录

`AbilityMetric` 不应只表示“一个名字和一个值类型”，还需要支撑未来更复杂的训练体系：

- 指标代码：稳定机器可读编码。
- 指标名称：展示名称。
- 维度：技术、身体、战术、心理、比赛表现、训练态度。
- 适用年龄段和水平段。
- 值类型：评分、次数、时间、距离、百分比、文本、标签。
- 单位：米、秒、分钟、次、分、百分比。
- 评分量表：1-5、1-10、百分制、自定义等级。
- 方向：越高越好、越低越好、区间最佳。
- 可见性：教练可见、家长可见、内部可见。
- 数据来源：训练观察、比赛、周期评测、体测、算法、人工修正。
- 是否原子指标：区分原始可记录数据和派生指标。
- 版本：指标定义变化后可以追踪历史。

指标之间的关系不应只有父子层级。需要通过 `MetricDependency` 或公式输入定义形成指标图谱，让任意指标能被多个评估体系复用。展示层级由 `MetricView` 和 `MetricViewNode` 承载。

### 指标记录

`PlayerMetricRecord` 是原子事实，必须保存：

- 学员、俱乐部、指标、值、发生时间。
- 来源类型。
- 关联活动、训练、比赛或评测。
- 记录人。
- 置信度。
- 备注。
- 输入设备或外部来源。
- 是否被修正。

### 派生指标

算法指标不应该覆盖原始指标。

派生指标通过 `DerivedMetricDefinition` 和 `MetricLineage` 记录：

- 算法名称和版本。
- 输入指标集合。
- 输入时间窗口。
- 权重。
- 输出指标。
- 输入记录 ID。
- 计算时间。

这样未来无论是 AI 运动表现评价、比赛贡献度、成长趋势、同龄人百分位，还是视频分析产出的跑动/触球数据，都可以落到同一套指标资产模型里，并继续被其他评估体系引用。

## 扩展字段机制

标准字段再完整，也不能预测所有俱乐部字段。扩展能力必须一开始就具备。

### 自定义字段定义

`CustomFieldDefinition` 应继续保留，并补齐：

- 字段 key。
- 展示名。
- 目标对象：学员、家长、教练、球队、活动、训练、比赛、指标记录。
- 值类型。
- 是否必填。
- 是否可筛选。
- 是否可导入导出。
- 是否家长可见。
- 排序。
- 默认值。
- 枚举选项。
- 校验规则。
- 状态和版本。

### 自定义字段值

应增加类型化字段值表：

- `custom_field_values`
- `club_id`
- `definition_id`
- `target_type`
- `target_id`
- `value_text`
- `value_number`
- `value_boolean`
- `value_date`
- `value_json`
- `created_by`
- `updated_by`

不要把所有扩展字段都塞进一个无结构 JSON。JSON 可以作为补充，但筛选、导入校验、权限和报表字段应有类型化存储。

### 字段升级路径

某个自定义字段如果在多个俱乐部反复出现，应该升级为标准字段。

升级标准：

- 至少 2-3 个俱乐部持续使用。
- 影响核心列表筛选或统计。
- 需要权限、审计或强校验。
- 与其他核心实体有稳定关系。

## 数据库能力调整建议

### 标准表增强

优先补齐：

- `student_profiles`：证件 hash、入训日期、状态、主位置、健康备注。
- `student_contacts`：多联系人和通知偏好。
- `student_operational_profiles`：渠道、区域、学校、当前沟通阶段、负责教练、运营备注。
- `regions`、`schools`、`acquisition_channels`：俱乐部级目录。

### 运营事实表

新增：

- `payment_events`
- `payment_reviews`
- `lesson_credit_ledger`
- `insurance_policies`
- `communication_logs`
- `attachments`
- `calendar_events`
- `event_participants`
- `training_sessions`
- `matches`
- `player_assessments`
- `player_metric_records`

其中部分对象领域层已有，当前数据库迁移还没有全部持久化，需要进入下一阶段 persistence 计划。

### 扩展表

新增：

- `custom_field_definitions`
- `custom_field_values`
- `external_system_connections`
- `external_table_mappings`
- `external_field_mappings`
- `external_sync_runs`
- `external_raw_records`
- `external_record_links`

## 产品规划结论

平台不应该为了避免复杂度而把运营字段都推迟到“以后模块”。正确做法是：

- 标准模型覆盖青训俱乐部的基础运营事实。
- 功能流程可以分阶段上线。
- MVP 只从训练、比赛、日程和评测开始；收费、保险和课时只做线下确认状态同步。
- 数据容器和字段扩展能力要提前设计。
- WPS 表格进入 integration 层，但其中反映出的业务字段要反哺产品模型。
- 球员能力评估要坚持原子指标、来源记录、算法派生和血缘追踪。

这样才能同时满足第一个俱乐部的真实业务，也能让后续俱乐部在新增字段时不用重构系统。
