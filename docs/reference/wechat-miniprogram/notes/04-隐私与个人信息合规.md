## 平台要求与默认机制 `[官方]`

- 隐私功能启用时间曾从 2023-09-15 延期到 **2023-10-17**。此后不论 `app.json` 是否配置 `__usePrivacyCheck__` 都会启用；不能把缺少该字段当作当前缺陷，也无需为启用功能补这个旧开关。见授权指南“更新说明”。
- 后台《小程序用户隐私保护指引》须声明实际处理的信息与用途。缺少相应声明、未声明隐私协议或错误勾选未采集隐私，会导致接口权限问题；本地源码无法证明后台状态。
- **官方默认弹窗可完成同意链路**：隐私调用需要授权、开发者未响应 `wx.onNeedPrivacyAuthorization` 事件时，微信会主动弹出官方弹窗。同意后继续接口调用，拒绝时报错。它包含与手机号授权耦合的样式，无需开发者先实现自绘弹窗。见授权指南“六、官方隐私弹窗功能说明”。
- 拒绝后不足 10 秒再次调用，可能直接返回拒绝错误而不再弹窗。不得自动循环重试；须让用户理解失败并自主选择重试或退出。
- 静态“同意隐私政策”文字本身不产生平台同意记录，但**文字不是官方同意按钮**也不能反向证明**官方默认弹窗不会工作**。

## 可选的自定义接入方式 `[官方]`

| 方式 | 用途与边界 |
| --- | --- |
| 默认官方弹窗 | 本项目可优先真机验证的现有路径；仍须正确配置后台声明并处理拒绝结果 |
| `wx.getPrivacySetting` + 同意按钮 | 需要提前展示协议时主动查询 `needAuthorization`，使用 `wx.openPrivacyContract` 和 `open-type="agreePrivacyAuthorization"` 完成同步 |
| `wx.onNeedPrivacyAuthorization` | 需要自定义界面时监听并按官方协议完成响应；监听本身不等于已经取得同意 |
| `wx.requirePrivacyAuthorize` | 主动触发隐私授权流程的可选入口，不是每个项目必须调用的前置 API |

从基础库 2.32.3 起可使用 `open-type="getPhoneNumber|agreePrivacyAuthorization"` 等耦合按钮。是否自定义属于交互选择，不是仅凭源码检索即可判定的合规门禁。`<input type="nickname">` 的未同意降级行为另见正文，不能把所有能力都视为同一种触发机制。

## 本项目实际处理的信息

| 处理的信息 | 当前接口/场景 | 核对要求 |
| --- | --- | --- |
| 手机号 | `pages/login/index.wxml` 的 `getPhoneNumber`；用于匹配俱乐部身份 | 后台声明、用户同意/拒绝、手机号返回 code 与服务端身份匹配分开验证 |
| 剪切板 | `pages/parent/coaches/index.ts` 的 `wx.setClipboardData`；复制教练微信号 | 官方对照将写入也归入“读取你的剪切板”；核对声明和默认弹窗/拒绝行为 |
| 人工输入的身份信息 | 球探等业务表单与后端处理 | 无新增 wx 隐私 API 不代表没有收集个人信息，目的、范围、存储与删除承诺仍须一致 |
| 相册、照片、位置、头像昵称等 | 新增时逐项对照官方接口表 | 后台声明、平台授权、系统权限及拒绝降级分别核对，不提前认定已批准 |

指引还需如实填写处理目的、存储期限、对外提供承诺、用户权益与联系方式、第三方服务商信息。不能使用与实际数据处理不符的示例期限。隐私同意与系统权限是不同层次。

## 当前证据与尚未闭合的门禁 `[本项目]`

- **2026-10-21源码确认**：现有手机号按钮和剪切板调用；优化提交已新增 `utils/privacy.ts` 与 `components/privacy-authorize`，App注册隐私监听、登录页包含自定义同意入口。旧“未发现自定义同步”的10-18结论已过时。源码/单测不等于后台声明或真机授权通过。
- **不能据此断言**：登录直接不可用、必须增加自绘弹窗或旧开关、后台指引必然未配置。
- **待后台确认**：声明是否覆盖手机号、剪切板及人工录入信息，用途/期限/联系方式与实际处理是否一致；未核验不写成“未实现”。
- **待真机确认**：全新用户/新增能力的首次提示、查看官方协议、同意后手机号成功、拒绝后退出/显式重试，以及复制教练微信号的拒绝路径。开发者工具合成测试不能替代这些证据。
- **产品独立门禁**：账号注销/数据删除申请、处理结果及留存规则与指引承诺一致；退出登录不等于注销。未完整验收不能写成完成。

## 推进顺序

1. 回读后台隐私指引与对应声明，记录日期和不含凭据的结论。
2. 验证当前自定义授权监听/同意/拒绝链路，并验证未接管场景的官方默认弹窗；不将旧无自定义实现的假设继续用于验收。
3. 仅当真机发现明确失败或产品确需提前展示时，再制定最小代码修复；同意前不执行收集，拒绝不循环触发。
4. 新增能力先核对后台声明与授权方案，执行首次/已同意/拒绝/新增能力回归；记录具体接口与错误，不把“零命中某 API”当作运行结果。
5. 提审前完成账号权益路径、隐私指引和真实身份业务验收。当前任务仅纠正文档，不替代上述平台与手机验证。
