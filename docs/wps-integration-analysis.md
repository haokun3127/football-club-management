# WPS 数据同步接入分析

## 背景

第一个俱乐部已经在 WPS 在线文档中维护业务表格，并且这些表格已经形成日常运营体系。平台目标仍然是保持统一后台能力，同时允许不同俱乐部有不同的小程序交互与业务呈现。

本次分析基于 4 份现有表格样本：

- `(用户表)全量用户.xlsx`
- `(充值事件表)交费事件.xlsx`
- `(到课事件表（25-26春夏）)2025-2026春夏.xlsx`
- `(保险购买事件表)保险购买.xlsx`

## 当前数据库适配度

当前迁移 `0001_platform_foundation.sql` 已覆盖多俱乐部、用户账号、家长、学员、教练、球队和队员关系。领域层已经有统一活动日历、活动参与记录、训练、比赛、评测与衍生指标等核心模型。

但从这批 WPS 表格看，数据库持久化目前还不能完整承接该俱乐部的现有运营数据。

| WPS 表 | 主要字段 | 当前适配度 | 需要补齐 |
| --- | --- | --- | --- |
| 全量用户 | 身份证号、渠道、区域、学校、队伍名称、教练、学员状态、手机、微信、充值笔数、保险到期、沟通反馈、签到次数 | 部分适配 | 学员外部标识、身份证号、学校/区域/渠道、微信、状态、CRM 反馈、运营汇总快照 |
| 交费事件 | 身份证号、收费日期、充值类型、金额、课时、缴费证明、审核、公司实收、同步状态 | 不适配 | 收费/充值事件、课时账户流水、审核流、附件凭证、同步状态 |
| 到课事件 | 身份证号、阶段、队伍、教练、第 1-27 周、充值课时、划课、签到、剩余课时 | 概念适配，持久化不足 | 活动/训练课持久化、出勤事实表、课时消耗流水、宽表到规范事实表的转换 |
| 保险购买 | 投保日期、身份证号、保险到期、保单号、运动项目、购买公司、审核、备注 | 不适配 | 保险购买事件/保单扩展、审核状态、保单号、保险公司、到期提醒 |

结论：现有骨架方向正确，但要接 WPS 数据，需要新增“运营扩展事实”和“外部系统同步”两类能力；不建议把核心数据模型改成 WPS 表格结构。

## 是否应在微信小程序侧做 WPS 同步

不建议。

小程序可以做定制展示、交互入口、同步状态查看、手动触发同步，但不应该承担 WPS 数据同步和转换逻辑。原因：

- WPS 凭证、开发者密钥、文档权限不能暴露在客户端。
- 小程序运行环境不适合后台定时同步、失败重试、幂等控制和冲突处理。
- 每个俱乐部的小程序定制不同，如果同步逻辑放前端，会让集成逻辑被复制到多个前端版本。
- 双向同步需要审计、锁定数据归属、字段映射版本管理，这些都属于后台能力。
- WPS API、下载文件、历史版本、限流和授权变化应由后端连接器统一隔离。

更合理的理解是：为该俱乐部做一个“小程序可调用的俱乐部适配 API”，但 API 背后的同步、转换、对账、落库都在服务端完成。

## 推荐架构

把 WPS 当作外部系统，而不是平台核心模型。

```mermaid
flowchart LR
  WPS["WPS 在线文档/导出文件"] --> Connector["WPS Connector"]
  Connector --> Raw["原始记录/同步批次"]
  Raw --> Mapper["字段映射与转换器"]
  Mapper --> Commands["领域命令/业务事件"]
  Commands --> Core["平台核心数据库"]
  Core --> API["统一后台 API"]
  API --> MiniProgram["定制微信小程序"]
  API --> Admin["运营/管理后台"]
  Admin --> SyncStatus["同步状态、错误处理、人工确认"]
```

### 1. 连接器层

新增 WPS 连接器，负责：

- 读取 WPS 文档或下载文档版本。
- 支持手动上传 Excel 作为降级通道。
- 记录每次同步批次、来源文件、版本、操作人、开始结束时间。
- 将原始行存入 staging，不直接写核心业务表。

WPS 官方开放平台提供文档信息、文档下载地址、历史版本、上传和更新文档内容等接口能力，具体接入能力需要在实施前以金山文档开放平台的当前文档和该俱乐部账号授权条件为准。

### 2. 映射配置层

每个俱乐部可以有不同表格和字段名，因此字段映射必须配置化：

- `external_system_connections`
- `external_table_mappings`
- `external_field_mappings`
- `external_sync_runs`
- `external_raw_records`
- `external_record_links`

这些表属于 integration 层，不污染核心业务模型。

### 3. 规范化转换层

将 WPS 行转换为平台领域命令，而不是直接复制字段：

- 全量用户 -> 学员、家长联系方式、球队关系、教练引用、学员运营扩展字段。
- 交费事件 -> 充值/收费事件、课时入账流水、审核状态、凭证附件。
- 到课事件 -> 将第 1-27 周宽表拆成训练/活动参与事实，关联队伍、学员、教练和阶段。
- 保险购买 -> 保险购买事件/保单记录，关联学员和到期提醒。

### 4. 同步策略

MVP 阶段建议只做单向同步：

- WPS -> 平台：导入已有体系，平台建立统一视图。
- 平台 -> WPS：暂缓，只做必要的同步状态回写或导出报表。

等数据归属明确后，再考虑双向同步。双向同步必须先定义字段所有权，例如“收费审核以 WPS 为准，训练出勤以平台为准，学员基础信息以后台为准”。

收费、保险和课时在 MVP 中以线下确认后的 WPS/后台确认状态为准。平台不在 MVP 内发起线上收费、在线投保、退款、发票或财务结算，但必须承接这些线下流程产生的运营事实和状态流转：课时入账、消课/调整、剩余课时、保险是否有效、保险到期、审核状态和来源审计。

### 5. 幂等和冲突处理

同步不能简单按姓名覆盖。推荐主键优先级：

1. 身份证号，作为当前样本中最稳定的学员外部标识。
2. WPS 行 ID 或行位置 + 文档版本。
3. 行内容 hash，用于检测变更。

每次转换要保留：

- 外部来源。
- 外部记录 ID。
- 上一次同步 hash。
- 转换状态。
- 错误原因。
- 核心记录 ID 映射。

## 对核心骨架的影响

不需要大改核心骨架。建议只做三个低侵入扩展：

1. 在平台基础数据上补充外部标识与运营扩展字段能力。
2. 增加收费、保险、课时账户、出勤持久化等运营事实表。
3. 增加 integration 命名空间，承载 WPS 连接器、映射配置、同步批次和原始记录。

核心领域仍保持：

- 多俱乐部隔离。
- 学员、家长、教练、球队是基础实体。
- 日历活动和活动参与记录是训练、比赛、其他活动的统一事实。
- 评测与衍生指标继续独立演进。

## 工程实施建议

### 阶段 1：Excel 快照导入

先做一个可重复运行的 Excel 导入器，作为 WPS 导出文件和历史数据回放的兼容路径：

- 读取 4 类表。
- 写入 staging。
- 生成导入预览和错误报告。
- 只在人工确认后写入核心表。

这样可以验证字段映射、数据质量和数据库缺口。

### 阶段 2：WPS 连接器与同步策略

在 Excel 导入稳定后，对接 WPS 文档；架构上从一开始就按后端 connector 设计，不把 WPS API 放到小程序侧：

- 保存 WPS 文档 token 与授权信息。
- 拉取最新版本或下载文件。
- 复用阶段 1 的解析、映射、校验和写入流程。
- 支持俱乐部后台配置同步频率、字段映射、自动确认规则、冲突策略和同步状态查看。

### 阶段 3：管理端同步工作台

提供同步状态和人工处理入口：

- 最近同步时间。
- 新增/更新/跳过/失败数量。
- 冲突记录。
- 字段映射版本。
- 手动重试。

小程序只需要看到结果或触发后台任务，不承担同步逻辑。

详细实现口径见 [WPS Realtime Sync And Status Flow Plan](./wps-realtime-sync-and-status-flow-plan.md)。

## 最终判断

你的理解“做 API 翻译各个方向的数据”是对的，但工程落点不应该放在微信小程序侧，而应该放在后端 integration/connector 层。

这样既能快速服务第一个俱乐部的 WPS 工作流，又不会把平台核心骨架绑定到某一个俱乐部的表格格式。未来第二个、第三个俱乐部如果也有飞书、多维表、Excel、企业微信表单等来源，可以复用同一套“外部系统 -> staging -> 映射 -> 领域命令 -> 核心数据库”的接入模型。
