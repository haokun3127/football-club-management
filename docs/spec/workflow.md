# 项目开发与文档流程

> Status: **Active** | Owner: **Engineering** | Reviewed: 2026-10-14

本文件是项目级流程补充。Trellis 的任务生命周期、步骤注入和状态机制以受托管的 `.trellis/workflow.md` 为准，**不在这里复制并维护第二份阶段流程**。

## 标准闭环

1. **接单/定界**：从 [规范中心](README.md) 读取产品、API、设计和质量要求；查最新 [状态](../status/current.md)，校验远端目标分支与工作区。非微小需求建立 Trellis 任务，明确 PRD、验收、排除事项。
2. **设计/评审**：必要时补 `design.md`、影响图、依赖和 ADR；未经授权的业务/权限/数据变更不能夹在 UI 修改中。
3. **小批实现**：仅修改白名单文件，真实 API 与 Figma 设计同时约束结果；禁止借外观修改引入伪数据。
4. **验证**：单测、typecheck、全量门禁、真实路由与数据读回、Figma 对照截图**分别记录**；各维度未验证不能写“已通过”。
5. **审查/提交**：显式列出修改文件、提交固定 commit；只把必要源代码推送 GitHub。LocalHarness 或微信开发者工具必须验证自己拉到该 SHA；push 不能冒充同步成功或视觉通过。
6. **反馈/暂停**：记录本轮缺陷、证据和未验证项；测试意见未回来之前不自动开始下一轮开发。下一轮需要明确的需求/批准。

## 规范变更

发生可重复的工程问题时，在同一 PR 修改本目录单一权威并更新必要兼容入口；历史任务只记录本轮如何发现，不再附加另一份活跃规则。

## 路由选择

- 产品/页面改动：先锁定在线 Figma 当前节点，再检查现有页面与真实业务契约。
- API/数据改动：先核对 `docs/spec/api/` 和 OpenAPI、迁移/测试，再确定 deploy 与回滚边界。
- 文档修改：先查 [governance.md](governance.md) 和 [ADR](../decisions/README.md)，不得随意建平行目录。

验收严格程度和证据形式见 [quality-gates.md](quality-gates.md)。
