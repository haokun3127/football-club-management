## 5. 开发与完成门槛

1. 开始修改前：引用现有需求 ID、画板 ID/状态、可复用代码和接口；读取本批 get_design_context 与截图。设计没读到则不自行编造 UI。
2. 修改范围：复用既有组件、主题、路由和业务身份，补真实数据；不将 Figma 示例值、系统状态栏或胶囊占位当业务代码照抄。
3. 行为检查：正常、空态、加载失败、撤权、并发冲突、重试；敏感数据使用白名单；状态与数据读回一致。
4. 视觉检查：同一页面、同一状态及等价数据对照 Figma 和微信开发工具；主按钮、入口、字体/间距/边界和滚动分别验收。合成截图只证明渲染。
5. 完成记录：功能通过、视觉通过、真实环境通过分别记证据；测试通过不替代设计验收。完成一个可追溯批次再整理其提交；禁止一次提交整个混合工作区。

状态统一：只有记录 / 已设计 / 已实现待验 / 已验收；“已实现待验”须列尚缺的设计或真实运行证据。沿用现有任务，后续在 requirements-design-map.md 和 checkpoint 更新，不新建竞争看板。
