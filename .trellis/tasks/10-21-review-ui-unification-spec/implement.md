# 分批实施与必要验证

v1.1 · 2026-10-21 · **用户已批准开发，分批执行中**。2026-10-21用户同意按v1.1开始开发，包含单一P基线，不再逐个询问原O-01～03。

## 1. 有向依赖与每批退出条件

`整版评审 → B1 → {B2、B3、B4、B5} → B6`。

四个业务批次只依赖公共基础，不互相等待。实际可按B2→B3→B4→B5顺序完成；这个顺序不是硬依赖。雷达、最终图片或Figma更新有问题时，只暂停对应功能的验收。

| 批次 | 输入 | 实施产物 | 本批结束条件 |
| --- | --- | --- | --- |
| B1 通用控件与主题 | 批准PRD；现有token/组件/路由 | 锁定TDesign稳定版本、npm构建、主题映射、通用控件迁移及路由盘点 | AC-03a、AC-04a/b通过；公共组件调用兼容；保留自绘项有原因 |
| B2 日程 | B1基础组件；现有两端活动数据 | Calendar公开API适配结论、一个共享周/月组件、两端接入和日期选择器 | AC-02a～d通过；不能只证明官方日期选择器能打开 |
| B3 登录与角色 | B1；原登录/会话/隐私链路 | UI、素材、最小角色偏好存储及后台默认配置、auto-active-role-v1分支 | AC-01a～c通过；旧客户端分支保留；最终素材未完成时只能标角色逻辑完成，不能整批通过 |

若B5早于B2/B4完成，先链接现有日程/能力页，保证teamId传递；B2/B4随后在原入口替换组件，B6只补一次衔接检查。无需等所有技术选型完成才开始B1。

## 2. 开发输入与范围控制

- 按当前HEAD/脏工作区接续，不切分支或覆盖他人改动；按项目要求读取trellis-before-dev及涉及层的规范。
- 路由清单从当前app.json生成一次，记录控件类别、使用页和迁移归属。全局控件使用处都需迁移，但不意味着所有页面组合重验。
- 日历适配验证只在B2做；ECharts/Canvas/包体初测只在B4做，不做多库竞赛。精确依赖版本在对应批锁定并留记录。
- Figma已有对应状态可参考并记差异；本轮未要求改图，不把改完全部Figma作为门禁。原生代表页截图是这次实现的视觉验收材料。
- 数据复用现有develop合成样本；B5只补第二支持久化球队、一个同名/无权队伍用例；B4只补完整已确认历史及批准标准样本。只在非生产准备必要数据，不重置审查账号或引入生产数据。
- 协议与后台隐私声明仅在B3核对；若留档超过项目时效或准备发布则刷新，不在每批重新查一次。

停止条件：本批AC、相应检查通过且无具体未解决问题，即进入下一批；只有代码/依赖变化、失败或新证据才补受影响检查。布局盘点覆盖全部受改路由，边界状态集中覆盖公共组件，避免生成全页×全状态×全设备矩阵。

不将出勤自动记录、模板复制、比分、战术板、后台全部权限等未修改功能加入新的人工交叉验收。既有自动回归继续运行；若某个实现实际改动其逻辑，才把相应行为测试加到该批，并写出触发原因。

## 4. 检查命令与去重

沿用项目Node24、pnpm10.33.0。开发中先跑受改包的typecheck和定向测试；当前命令入口为：

```sh
pnpm --filter @football-club/miniprogram-cq-talent typecheck
pnpm --filter @football-club/miniprogram-cq-talent test
```

定向用例按现有Vitest配置筛选；API合同变化时仅补相关API/domain用例。公共组件验证通过后不再为每个调用页重跑同一份测试。

B6在最终源码上选择**一次**：

- 普通开发交付：`pnpm check`。
- 若本次同时形成正式交付候选：`pnpm check:delivery`，它已包含check和构建，替代上一项；同一轮不再串行运行check+check:delivery。

小程序策略报告`pnpm check:miniprogram-policy`在最终相关改动上审阅一次；检查器恒定exit0不代表问题已解决。只有实际修改策略脚本/规则才额外运行其单测，本轮不要求无关检查器测试。

官方npm构建在B1/新增图表依赖的B4后执行；最终构建产物统一测包体一次，不把原文件求和当发布依据。未安排上传或发布时，不以补齐生产环境验收为本轮开发完成条件。
